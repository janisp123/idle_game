# STABILIZATION-001 — sequential audit and fix protocol
Owner request 2026-11-28: plan testing so fixes do not overlap. This is a testing/coordination plan, not approval of new mechanics. Reference: #231 merged 9624c14494e0ad31b5a8dafd63081ed1bcd1178a, 223 tests, seven CI workflows. Reconfirm deployed version before browser baselines.
## Mandatory coordination
- One active stabilization implementation PR at a time, across Chat, CW and Codex. Parallel investigation is read-only, with separate evidence files; no parallel edits to shared source or shared regression fixtures. Do not start the next fix until prior PR is merged, main SHA verified, and public change deployed and smoke-tested. Stop on unexpected behavior, failing CI, competing PR or changed base. All other feature work is deferred.
- At each start fetch remote main TD_LIST first, then AGENTS, WORK_CHECKPOINT, DECISIONS, relevant mechanic source and all open PRs/branches. Check for overlap by changed paths AND behavioral dependencies. Declare exact writable path allowlist, affected shared interfaces, base SHA, fixture IDs, expected invariant changes and explicit exclusions in PR body before edits. Any new file/dependency outside scope requires revising the reservation before edits; no duplicate agent ownership.
- Main is the only new implementation base. Never reuse stale long-lived feature branches or stack unreviewed code. One defect or closely inseparable transaction per PR. No unrelated refactor, formatting sweep, dependency upgrade, balance retuning or cleanup bundled with a fix. Shared files (engine, manager-lanes, battle-group, timeline, team-combat, manager-app, index, shared tests) may be touched in different sequential phases, never concurrently. Keep docs changes within the same checked PR; no history rewrite.
- Ledger per work item: ID, agent, base SHA, branch/PR, owned files/interfaces, status (AUDIT/REPRODUCED/FIXING/TESTING/MERGED/DEPLOYED/BLOCKED), test evidence, previous/current metrics, remaining work. Use TD_LIST and WORK_CHECKPOINT plus PR evidence. If a later phase discovers an earlier defect, record it, stop affected tests, reopen that phase as a new fix against current main, rerun downstream dependents. Do not quietly patch an earlier subsystem inside a later PR.

## Test ladder per fix
1. Reproduce failing case against current main (actual engine, not copied formulas); store seed, exact input, expected/actual and output. Add a targeted regression that fails before fix and passes afterwards where applicable.
2. Run impacted module and integration tests including all transitive dependents. For logic-neutral optimizations require exact equality of seeded results; for intended bug fixes list exactly which outputs should change and why. Never regenerate golden fixtures simply to make a test green.
3. Full regression: all existing Node tests, seven applicable code CI workflows, Chromium mobile and desktop. Recheck natural progression/old save behavior as appropriate; no merge until final-head required checks pass and no overlapping changes. Existing docs-only workflows are not sufficient for a production code fix.
4. Benchmark on same runner/runtime, deterministic inputs, warmups, repeated runs and median/p95 (at least 10 repeats where practical); record wall time, heap/trace allocation, bundle/transfer bytes, save size/writes per minute, tick backlog/long tasks, offline latency. Record actual results, including regressions. A performance change must show improvement in its target metric without correctness regression; no arbitrary claimed speedup. Cross-device figures labeled separately.
5. Merge via existing owner-approved alpha gates, verify main and actual Pages version independently, save evidence and next exact step. Update baseline only for intended, reviewed behavioral changes; retain original baseline and previous evidence for comparison. If code fails deployment smoke, stop next package and fix/revert with checked PR, not a silent reset.
## Cross-system scenarios
- New game -> recruits -> character class at 20 -> specialization at 30 -> gear tiers -> tower qualification -> personal raid -> clan contribution/construction/raid -> finite completion. Natural simulated daily progression, no max button to skip the path; max button used separately for endgame benchmark.
- Battle boundary -> change race/class/stance -> hide/reload -> exact frozen settlement -> coin and upgrade reconciliation.
- Tower/raid started -> leave/reload past finish -> single payout/buff -> arena resume -> no duplicated training or reward.
- Two tabs and injected storage failure during a reward/clock update -> retain last valid commit, no duplicated coins.
- Each fixed system reruns previously accepted upstream invariants and directly downstream tests; final suite includes all of them.
## Decisions and limits
Sequential implementation intentionally trades speed for isolation; audits and standalone read-only profiling may overlap. Do not interpret plan as authorization to invent finite cap values, change raid rules or introduce features. No actual new test execution or performance improvement claimed in this planning change. Initial full-checkout inventory and deployment confirmation still outstanding at plan writing.
