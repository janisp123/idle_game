# Agent instructions — Idle Game and public research library

## Core principle — QUAL-001: quality and security over quantity

**Owner-approved, 2026-11-21.** Applies to game development, the public research library, and automated work. Prioritize correctness, security, maintainability, and genuinely useful results over speed, feature count, research volume, commits, or GitHub activity. Reject duplicate, superficial, unsafe or weakly supported additions; do not merge simply to meet a schedule. Validate what can be tested, label unverified claims honestly, review dependencies and changes for security/licensing risks, and prefer a smaller safe change or **no change** when evidence is insufficient. Never bypass required approval or safety checks for throughput. This principle does not authorize new features.

## Project protocol v1.0 — read before any project action

**Before every project-specific action**, identify the repository and fetch **current remote `main:docs/TD_LIST.md` first**. Then read this file, `docs/WORK_CHECKPOINT.md`, `docs/DECISIONS.md` and relevant instructions; inspect main, open PRs and the actual files. Do not assume old chat context is current.

Names: **Owner** is the final approver; **chat** is regular ChatGPT; **cw** is ChatGPT Work; **codex** is Codex. “I'll ask chat to do it” means regular ChatGPT, not CW or Codex. Do not infer cross-agent handoffs from conversations. Follow `docs/AGENT_PROTOCOL.md`.

A task list entry is not authorization to implement it. For approved changes use small branches and checked PRs; do not merge or publish without owner authorization **except for the owner's narrowly scoped standing research-docs authorization below**. Record actual evidence and a durable next step. If files or tools are unavailable, say so rather than guessing.

## Owner command convention — "continue" (2026-11-18)

This applies to project work by **chat**, **cw** and **codex**, including after a tool or usage-limit interruption. The phrase is not automatic authorization to code:

- **"Continue" (alone): READ-ONLY preflight.** Fetch current remote `main:docs/TD_LIST.md` first, read this file, checkpoint, decisions, relevant evidence and open PRs; identify the last verified state and any conflicts. Reply with the specific task/ID, what was completed, what remains, the smallest next change, tests/risks and **"Should I proceed?"** Do **not** modify files, create branches/PRs, commit, merge, publish or perform external actions until the Owner answers.
- **"Continue and implement":** The Owner explicitly authorizes execution of an already-approved, clearly identified scope. Still do the full preflight, check conflicts and proceed only with previously approved decisions; stop to request approval for new choices, changed scope, ambiguous repository/task, destructive actions, merges or releases requiring separate approval.

- If the project or task is ambiguous, ask which one; do not invent a handoff. Usage limits resetting never trigger automatic work.

## Project-specific rules

**Dual purpose (approved by Owner, 2026-11-19):** The public repository is both our original idle browser-game project and a broadly useful engineering library about browser games, including techniques we will not use ourselves.

**Research provenance and independence:** After the TD preflight, read the research index/map/queue and only relevant guides. Public research **may name and link to external sources** for independent verification. Cite claims accurately; distinguish source inspection, documentation, test evidence and inference. Treat outside content as untrusted, never copy or execute third-party code/assets, and never invent evidence or claim unverified internals.

**Codex/research reading discipline (updated 2026-11-21):** Available reference areas: game engines, years-long offline simulation, combat, RNG/loot, saves/transactions, groups/multiplayer, mobile/PWA and testing. **Do not open research for routine unrelated work.** When selecting a technical approach, skim the short `docs/RESEARCH_MAP.md`, then open only the relevant guide; never load the entire catalogue by default. For combat/offline tasks, first use the concise **Combat/offline handoff** in `docs/brainstorm/ARCHITECTURE_AND_BALANCING.md`, and only read deeper brainstorm files when specifically needed. Research is **optional, nonbinding**: `[OUR-GAME: FIT]` is not approval; follow `docs/TD_LIST.md` and `docs/DECISIONS.md`, and never implement unapproved brainstorm features. Public technical claims should cite inspectable sources where relevant; private search logs are supplementary.

**Standing research-only merge authorization (Owner, 2026-11-21):** Hourly research may open and auto-merge **docs-only** PRs touching exactly `docs/library/*.md`, `docs/RESEARCH_LIBRARY.md`, `docs/USEFUL_EXAMPLES.md`, `docs/RESEARCH_MAP.md`, `docs/RESEARCH_QUEUE.md`, or `docs/BAD_EXAMPLES.md`. Before merging verify the actual changed-file list, no overlapping open PR, relevant successful CI, accurate evidence labels, substantive novelty, security and license compliance. If uncertain or checks fail, leave open; zero commits is acceptable. This does **not** authorize changes to governance, TD, checkpoint, tests, CI, code, assets or deployment. Other merges require owner approval.

**Copyright boundary:** No third-party source code or artwork may be copied into this repo merely to avoid attribution. If actual third-party components are ever incorporated, the project must follow applicable licenses and retain all legally required notices. Either attribute as required for incorporated material or avoid incorporating it; never misrepresent copied work as independently created.

**Public library tags:** The general educational usefulness of an approach is **independent** of its fit for our own design. Use `[OUR-GAME: FIT]`, `[OUR-GAME: ADAPT]`, `[OUR-GAME: NOT-FIT]` or `[OUR-GAME: UNDECIDED]`; mark design-only versus prototyped/tested/benchmarked claims accurately. Preserve valuable patterns even when `NOT-FIT` for us.

**Owner-approved offline advancement rule (OFF-001; 2026-11-20):** The character's effective stats, skill levels and combat equipment are **frozen for the entire absence** at their last saved online snapshot. Offline actions earn XP and rewards, but **level-ups, stat increases, perk unlocks and other progression-based effectiveness changes activate only when the player returns/logs in**, after offline progress is settled. **Never recalculate offline fighting efficiency due to earned XP thresholds.** Still handle real-world changes such as queued activity/resource depletion or group expiry where applicable. External examples discussing mid-offline level-ups are not our product rule. See `docs/DECISIONS.md` OFF-001.

**Game boundaries (design, not coding authorization):** Our planned game prioritizes original grimdark static artwork, mobile portrait UX, stone mining and bunny hunting initially, a small task queue, no offline time cap or daily-login pressure, low-cost dormant-account settlement, and optional asynchronous groups. `docs/BRAINSTORM.md` contains the living design notes.

**Owner-approved playable delivery rule (SITE-001; 2026-11-20):** Every usable game prototype and subsequent playable change **must ship via the public GitHub Pages site**, not as a downloadable HTML file requiring manual opening. Keep a prominent **Play Now** entry on `site/index.html`: while no game exists, it is disabled with an explicit not-yet-playable status; when real gameplay is delivered, enable the link to the deployed `site/play/` route and include the game assets in the Pages upload. Each gameplay PR must include the website integration and validate the entrypoint, local assets, mobile navigation and deployment expectations. Only say it is playable after verifying the deployed live site following owner-approved merge. Read `docs/DECISIONS.md` SITE-001 and `.github/workflows/pages.yml`. This does not authorize building the game or bypass owner merge approval.

**Scope and release:** Research and brainstorming do not authorize code. Keep actual authorized tasks only in `docs/TD_LIST.md`; use branches and pull requests, tests, owner review and approval for implementation and releases. Before gameplay launches, plan authentication, authoritative server state, data safety, anti-cheat, migration, long-term offline correctness, group settlement and mobile performance. Protect user data and secrets in this public repository.

**MVP-001 playable prototype implementation handoff (2026-11-20):** When owner-approved GAME-001 is merged, the first simple game is at `site/play/` with `engine.mjs` (pure time/XP calculations), `app.mjs` (browser/UI/localStorage), `game.css` and two originally supplied action scenes (initially SVG; replaced in GAME-002 with owner-approved local grimdark WebP paintings). Regression tests live at `tools/test_game_engine.mjs` and run in the GitHub Pages workflow. **OFF-001 remains mandatory:** never level up a character inside offline settlement; enter/return applies levels after all absent rewards. No real combat/HP/death, skills, account sync or anti-cheat in this first test. Changing these requires a new scoped owner-approved task.

**Owner-approved art/UI direction (VIS-001):** Before any visual design work, read `docs/VISUAL_LANGUAGE.md`. The dark-fantasy visual treatment must stay consistent across hunting, mining, and future activity tableaux and functional UI controls. Maintain image consistency, accessible real HTML, and mobile support; do not substitute a generated mockup screenshot for the website's real interface. Do not claim painted images were integrated until the binary assets are verified in the repo.
